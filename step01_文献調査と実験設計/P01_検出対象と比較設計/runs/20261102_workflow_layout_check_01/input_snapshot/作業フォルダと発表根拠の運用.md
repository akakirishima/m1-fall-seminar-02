# 作業フォルダから実行記録と発表へつなぐ運用

更新日：2026年11月2日。方針版：v1.7。
本人の説明に従い、やることごとに作業場所を分け、そこで行った処理と確認結果を記録し、その根拠から発表資料を作成する。

## 一つの作業フォルダ

P01からP14に専用フォルダを置く。
各工程の正しい保存先は[状態JSON](../research_state.json)の`work_packages`に登録する。
ファイル名の推測や全ログの読み込みから現在地を決めない。

```text
Pxx_作業名/
  README.md             目的、入力、出力、完了条件、現在地
  scripts/              保存した処理コード
  configs/              実行条件の案と確定設定
  runs/
    実行ID/
      manifest.json     実行の識別と入出力、成否、参照先
      code_snapshot/    実行時のコード
      実行結果.md        実施内容、確認結果、失敗、限界
      その他の出力       公開可能な集計と図表など
```

空のフォルダと`.gitkeep`は保存先の準備であり、実験や実装の完了ではない。
共通処理は既存の親ステップの`scripts/`や`research_tools/`で再利用し、各実行に実際に使ったコードを保存する。
完了済みの旧`stepXX/runs/`は元の場所で保持し、新規の記録は担当工程の`runs/`へ置く。
複数手法の最終評価はP12で、手法ごとに実行IDとmethod_idを分けて記録する。

## 記録する範囲

計画、コード作成、実行、確認、解釈を区別する。
文献調査は原典と確認範囲、設計は判断理由と未決事項、実行は入力、コード、設定、環境、開始終了、成否、出力を残す。
学習、推論、採点、保存結果の集計は、それぞれ新しい実行IDを発行する。
失敗や中断も記録し、動かなかった方式を低精度という性能結果に置き換えない。
数値と入力一覧の正本は実行出力で保持し、READMEと日報には実行IDと参照先を記す。

実行には[固定形式](AI向け記録形式.md)と[テンプレート](../templates/experiment_manifest.json)を使う。
新しい記録を追加したら、索引生成、記録検査、必要な内容確認を行う。
自動記録ランナーは未統合なので、フォルダを用意しただけで全情報が自動保存されるとは扱わない。

元動画、抽出画像、正解ラベル、患者対応、重み、機微なログはGit対象外のローカル保存先へ置く。
工程の共有記録には安全なIDと版、ローカル対応表への識別IDを残す。
「その工程の記録から追跡できること」と、すべての実データをそのフォルダやGitへコピーすることを区別する。

## PowerPointに使う根拠

スライドに載せる主張、表、グラフ、画像は、[発表根拠の対応表](../スライド/発表根拠の対応表.md)から実行IDと成果物へ対応付ける。
複数実行を集計した表なら、元の実行IDと集計実行の両方を記す。
論文の報告値には原典の書誌と条件、自分の実測には実行IDと評価条件、構想には未実施の表示を付ける。
確認前の結果、例示用の画像、未測定の数値を、検証済みの実験結果として載せない。

PowerPoint用に数値を手入力して別管理せず、保存された集計から表やグラフを作る。
画像と数値の一致、比較条件、対象データ、失敗の扱いを確認してから、読み取りを文章にする。
内容の確認と、スライドのはみ出しや可読性の確認は別々に行う。
過去の本人資料は背景と指摘の参照に使い、今回の結果の代わりにはしない。

## 旧記録の扱い

固定形式導入前のmanifestは、状態JSONの`legacy_manifests`へ対象を明示して登録する。
対象の記録だけを索引で`legacy_manifest`、`partial`として扱い、不足項目を推測で補わない。
新しい未完成のmanifestを自動的に旧形式へ振り替えない。
旧形式の所在を確認できても、モデルの動作、結果の妥当性、再現性を確認したことにはしない。
