# 研究全体の実行方針と結果の追跡

## 目的

研究の処理は、保存したコードを実行して行う。
各結果について「どのコードを、どの設定と入力で実行し、どこに出力したか」を後から確認できる状態にする。
この方針はSiamParseNet、YOLO、SAMのすべてに適用する。

学習と評価だけでなく、白黒変換、動画のフレーム抽出、ラベル変換、比較表の集計、グラフ作成、運動特徴量の計算も対象に含める。
画像や動画を見て判断した内容は目視確認として記録し、数値計算による結果とは区別する。

## 処理をコードに残す

各処理は役割を説明できるPythonファイルなどに保存する。
端末では、その保存済みファイルを起動する。
研究結果を作る処理を、保存されない端末の一時コードだけで済ませない。

たとえば「評価コードを動かした」と記録するだけでは不十分である。
評価コードの名前に加えて、モデルの重み、入力画像の一覧、正解ラベル、前処理、評価方法、出力先を記録する。
公開コードを呼び出すラッパーの場合は、ラッパーと呼び出された実装の両方を記録する。

## 実行IDと専用フォルダ

**実行ID**は、1回の実行を区別する名前である。
日時、処理名、短い一意の文字列をコードで組み合わせる。
例の形式は `YYYYMMDD_HHMMSS_color_model_gray_test_<短いID>` とする。
学習、評価、比較表の作成には、それぞれ別の実行IDを付ける。

新しい実行は次の構成を基準にする。
既存のカラー実験のフォルダは移動せず、今後の実行からこの構成へ移行する。

```text
step1_siamparsenet_reproduction/
  scripts/                        編集する学習用、評価用などのコード
  runs/
    <実行ID>/
      manifest.json               コード、設定、入力、出力、実行状態の対応
      config.json                 実際に使った最終設定
      inputs.csv                  入力ファイルまたは入力データ登録への参照
      outputs.csv                 出力ファイルの一覧と役割
      environment.json            Python、PyTorch、CUDA、GPUなど
      requirements-lock.txt       使用環境のパッケージ一覧
      code_snapshot/              実行した自作コードと利用実装の保存コピー
      logs/                       標準出力と標準エラー、経過時間
      artifacts/                  重み、予測マスク、CSV、比較画像など
      実行結果.md                 人が読む目的、結果、制約、再実行方法
```

同じ設定でも再実行時には別のIDとフォルダを作る。
完了したモデル、CSV、画像を次の実行で上書きしない。
途中再開は別の実行として扱い、再開元の実行IDとチェックポイント、再開ステップを記録する。

## 毎回記録する項目

| 項目 | 記録する内容 | 何を確認できるか |
|---|---|---|
| 実行の識別 | 実行ID、処理名、目的 | 何のために行った処理か |
| 状態 | 準備中、実行中、完了、失敗、中断、終了コード | 最後まで実行できたか |
| 日時 | タイムゾーン付き開始時刻、終了時刻、経過秒 | いつ、何時間実行したか |
| 実行方法 | Python実行ファイル、引数配列、作業ディレクトリ | 同じ処理をどう起動するか |
| コード | 起動コード、呼び出した実装、保存コピー、SHA-256 | 実行時にどの内容のコードを使ったか |
| 設定 | 初期値と引数を反映した最終値、前処理、乱数シード | どの条件で処理したか |
| 入力 | ファイルの役割、パス、SHA-256、画像IDや動画区間 | どのデータを使ったか |
| 親の結果 | 入力モデルや評価結果を作った実行IDとファイル | 前段階のどの結果に依存するか |
| 出力 | ファイルの役割、パス、SHA-256、件数 | どれが今回の成果物か |
| 環境 | Pythonとパッケージの版、CUDA、GPU、OS | どの環境で動かしたか |
| 確認 | 件数、非有限値、Train/Test重複、代表画像の確認 | 何を検証して完了としたか |

**SHA-256**は、ファイルの内容を識別するための値である。
ファイル名が同じでも内容が変われば識別値が変わるため、名前だけでモデルやコードを取り違えることを防げる。
Gitのコミットがある場合は併記するが、未コミットの修正もあるため、実行したファイルの保存コピーを残す。

大きなデータセットは毎回コピーしない。
最初に各入力画像とラベルの相対パス、内容のSHA-256、画像ID、動画IDを含むデータ一覧をコードで作り、その一覧と元データを保持する。
各実行は一覧の保存先とSHA-256、実際に使った分割や対象画像の一覧を記録する。
入力を変更した場合は新しいデータ一覧を作る。

学習の入力と、件数検査のために参照したTestラベルは役割を分けて記録する。
Testを参照しただけで「Testで学習した」と誤解されないよう、重み更新に使用した範囲を明記する。

## 出力から入力へたどる方法

各CSVには実行IDを付け、各結果レポートには実行記録へのリンクを付ける。
CSVは行に実行IDを追加し、PNGやMP4などは対応する出力一覧に実行IDとファイルパスを記録する。
比較画像には、構成した元画像と予測結果のIDも記録する。

予測マスクには元画像IDと動画IDを対応付ける。
動画のフレーム抽出には元動画の識別値、フレーム番号、時刻、抽出区間、抽出間隔を記録する。
運動特徴量のCSVには元フレームと予測マスクの対応を残す。

比較処理では、モデルを暗黙に読み直して別条件で推論するのではなく、比較対象の評価実行とCSVを入力として指定する。
新たな推論を行う場合は、別の評価実行として記録する。

たとえば白黒モデルの評価結果は、次のようにたどれる。

```text
白黒モデルのDiceレポート
  → 評価の実行IDとmanifest.json
  → 評価コードの実行時コピー、白黒変換設定、Test画像一覧、正解ラベル
  → 入力した白黒モデルのファイルとSHA-256、学習実行ID
  → 学習コードの実行時コピー、Train画像一覧、COCO初期重み、学習設定
```

## 実行記録を残すための実装順序

記録を毎回手で作るのではなく、共通の記録用コードを各処理から呼ぶ方式にする。
実行前に入力とコードを登録し、処理が終わったら出力と確認結果を登録する。
失敗や中断も記録し、途中成果物と完了成果物を区別する。

- [x] 共通の実行記録コードを保存済みファイルとして実装する。
- [x] 条件確認で一意の実行IDを発行し、新しい専用フォルダを作成する。
- [x] 条件確認でコードを保存し、設定、入力一覧、環境を実行前に記録する。
- [x] 保存された確認コードを実行し、標準出力とエラーをログに保存する。
- [x] 出力一覧とSHA-256を作り、出力識別値を検査する。
- [x] 成功と失敗の記録を検査し、終了コードと時刻を保存する。
- [x] 条件確認の実行結果Markdownを生成する。
- [x] 条件確認を[実験一覧](実験一覧.md)とStepのチェックリストに反映する。
- [ ] 強制終了など、通常の終了処理が動かない場合の中断状態の復旧を整備する。
- [x] カラーモデルの白黒Test評価（B）へ共通記録を組み込み、全Test画像と入力モデルを識別値付きで登録する。
- [x] 白黒学習、C評価、保存済み結果の比較へ共通記録を組み込むコードを作成する。
- [x] ユーザーの実行と明示的な依頼に基づく実行で、白黒学習、C評価、比較の記録を保存する。

共通記録コードは `research_tools/run_record.py` に実装し、2026年10月8日の白黒条件確認で使用した。
合成データによる成功と意図した失敗の記録も確認済みである。
通常のPython例外やKeyboardInterruptを扱う実装だが、強制終了や電源断では状態が実行中のまま残り得るため、時刻とログから後で中断を確認する。
実験Bでは全Test画像1,256枚の入力一覧と内容識別値を残し、評価コードへ組み込んで使用した。
全Train画像の入力一覧や白黒学習への組み込みは、次の実行前に整備する。
全Train入力を登録するコードは作成したが、一覧の生成とGPU動作はまだ実行していない。
現在の研究コード実行はユーザーが担当し、アシスタントは作成と静的レビュー、実行手順の整備を担当する。
外部の実験管理サービスは今回必須とせず、まずこのPCのファイルだけで追跡できる構成にする。

## 既存のカラー実験の扱い

すでに得たモデルや評価結果は再学習や移動をせず、現存ファイルから対応関係を整理する。
追記する記録には「後から整理した記録」と明示する。
実行時に保存されていなかった情報を、実行時に確認済みだったことにしない。

| 処理 | 現存する起動コード | 主要な入力 | 主要な出力 |
|---|---|---|---|
| カラー学習 | `step1_siamparsenet_reproduction/scripts/train_paper_like.py`（実装は `MICCAI20_SiamParseNet/train_semi_anneal_T.py`） | `all_data/`、`train_label.json`、`train_unlabel.json`、COCO初期重み | `step1_siamparsenet_reproduction/runs/paper_like/snapshots/B0020_S010000.pth` |
| カラーTest評価 | `step1_siamparsenet_reproduction/scripts/evaluate_public_test.py` | 上記の最終モデル、`all_data/` の公式Test画像、`test_label.json` | `results/public_test_final/` のCSVとレポート、`predictions/public_test_final/` のマスクと画像（いずれもStep 1配下） |

カラー学習には `run_config.json`、カラー評価には `metrics.json` があり、一部の条件や入力モデルの識別値を確認できる。
一方、実行時コードの保存コピーや全入力画像の内容識別値はまだ残していない。
現在のコードを保存しても、過去に実行した内容と完全に同一だったことの証明にはならない。
不足している項目は「未記録」として残し、今後の実行から記録をそろえる。

## 研究処理の完了条件

- [ ] 処理したコードがファイルとして保存されている。
- [ ] 実行時コードのコピーと内容識別値が残っている。
- [ ] 設定、入力、親の結果、出力の対応が記録されている。
- [ ] 成否と確認内容が記録されている。
- [ ] 実行結果Markdownから再実行方法と成果物を確認できる。
- [ ] 実験一覧とStepの進捗に反映されている。

結果を確認できただけで、追跡に必要な記録まで完了したことにはしない。
既存結果の処理完了と、今後追加する追跡記録の整備は別に管理する。

実行結果の文書には[テンプレート](templates/実行結果テンプレート.md)を使う。
記録から再実行できる条件をそろえるが、GPU演算や乱数による数値の完全一致まで保証するものではない。
